# QA Audit 모드 1단계 — 체크리스트 입력 설계

- 작성일: 2026-10-27
- 브랜치: `QA-assessment`
- 참고: `SL_AI_QA_자동감사_제안준비자료.docx` (VWAY 내부 제안 준비 자료, 이하 "제안 문서")

## 1. 배경과 의도

평가 스튜디오에 프로세스 모드·프로젝트 모드에 이어 **QA Audit 모드**를 추가한다. QA Audit 모드는 VWAY가 보유한 두 종류의 체크리스트로 산출물과 프로세스를 감사하고, 항목별 Pass/Fail과 프로세스 준수율을 담은 리포트를 만든다.

전체 기능은 4단계로 나눈다. 이 문서는 **1단계만** 다룬다.

| 단계 | 내용 |
|---|---|
| **1. 체크리스트 입력 (이 문서)** | VWAY Excel 2종 가져오기, 검증 오류 목록, AI 판정 기준 초안, QA 검토·확정, 프로세스↔산출물 연결 확정, 버전 관리 |
| 2. QA 커스텀 룰 | 존재 확인 / 두 위치 일치 / 지시문(LLM) 세 유형의 룰 편집 화면 |
| 3. 판정과 리포트 | 산출물 항목 Pass/Fail/보류, 프로세스 준수율, 인용·발견 위치 표시 |
| 4. Scorer 연동 | 프로젝트 모드 Scorer 엔진 목록에 "QA 체크리스트" 엔진 추가(다중 선택 시 평균) |

1단계의 목적은 **"QA가 확정한 체크리스트 세트"를 만들어 저장하는 것**이다. 2~4단계는 모두 이 확정본을 입력으로 쓴다. 엑셀을 그대로 판정에 쓰지 않고 **AI가 판정 기준 초안을 만들고 QA가 확인·확정한 항목만** 이후 판정에 쓴다(사용자 결정).

## 2. 목표 / 비목표 / 실패 조건

**목표**
- VWAY 템플릿 Excel 두 종(산출물 체크리스트, 프로세스 체크리스트)을 가져와 구조화된 체크리스트로 저장한다.
- 가져오기 오류(필수 열 누락, 중복 ID 등)를 목록으로 보여준다.
- 산출물 체크 항목마다 AI가 판정 기준·대상 위치·관련 BP·심각도 초안을 만들고, QA가 수정·확정한다.
- 프로세스 체크 항목마다 AI가 연결할 산출물 체크 ID와 관련 BP 초안을 만들고, QA가 수정·확정한다.
- 체크리스트를 버전으로 관리한다. 다시 가져오면 새 버전이 되고, 체크 ID가 같은 항목은 기존 확정 내용을 이어받는다.

**비목표 (1단계에서 하지 않음)**
- SL 원본 등 임의 형식 Excel의 열 매핑 화면(사용자 결정). 지원 형식은 3절(3.3 포함)의 VWAY 체크리스트들이다.
- 산출물 실제 판정, Pass/Fail 계산, 리포트(3단계).
- 커스텀 룰 편집(2단계). 단, 데이터 구조에는 룰을 붙일 자리를 둔다.
- Scorer 엔진 연동(4단계).
- 서버 DB. 저장은 기존처럼 브라우저 IndexedDB.
- 로컬 LLM 연결. 1단계는 기존 LLM 공급자 설정(기본 Anthropic)을 그대로 쓴다.

**실패 조건 (동작해도 실패로 보는 경우)**
- QA가 확정하지 않은 AI 초안이 판정에 쓰일 수 있는 상태가 되는 것.
- 다시 가져오기 때문에 QA가 확정한 내용이 말없이 사라지는 것.
- 엑셀의 원문(체크 ID, 검토 항목 문장)이 AI나 편집 과정에서 바뀌는 것. 원문은 항상 읽기 전용이다.
- 기존 프로세스 모드·프로젝트 모드 동작이 바뀌는 것.

## 3. 입력 형식 (VWAY 템플릿)

### 3.1 산출물 체크리스트 — `ASPICE_40_Template_체크리스트_통합임포트.xlsx`

- 시트 하나가 산출물 하나다. 현재 23개 시트(예: `1.프로젝트계획서`, `8.시스템 요구사항 명세서`, `22. 소프트웨어 소스코드`).
- 1행: codebeamer 필드명 `seq_no, item_id, col06, item_title, col35, col07, item_workflow_status_no, item_content, workitem_key_id_no`
- 2행: 한글 헤더 `No., 체크리트스 ID, 영역, 검토 항목 (필수), 적용 여부, 검토 결과, 상태, 검토 의견, 구분자`
- 3행부터 데이터. 현재 채워진 열은 `item_id`(예: `CH-PP-001`), `col06`(영역: 준수성·일관성·정확성·완전성·이해가능성·추적성 등), `item_title`(검토 항목)뿐이다.
- 시트 범위(`!ref`)가 실제 데이터보다 넓어 빈 행이 있다. `item_id`와 `item_title`이 모두 빈 행은 건너뛴다.

열 식별은 **1행의 codebeamer 필드명**으로 한다(2행 한글 헤더에 오타 "체크리트스"가 있으므로 2행에 의존하지 않는다). 1행 필드명이 없는 시트는 오류로 보고한다.

| 필드명 | 저장 필드 | 필수 |
|---|---|---|
| `item_id` | `checkId` | 예 |
| `item_title` | `question` | 예 |
| `col06` | `area` (앞뒤 공백 제거, 예: `"준수성 "` → `"준수성"`) | 아니오 |
| `col35` | `applicable` (`N`/`아니오`/`미적용`이면 false, 그 외·빈칸은 true) | 아니오 |
| 나머지 | 원본 보존용 `raw`에만 저장 | — |

시트 이름 → 산출물·프로세스 대응은 아래 기본 표로 자동 지정하고, QA가 시트 단위로 바꿀 수 있다. 앞 번호와 공백은 무시하고 이름으로 맞춘다(시트 `22.`가 두 개이므로 번호로 맞추면 안 된다).

| 시트(산출물) | 프로세스 |
|---|---|
| 프로젝트계획서 | MAN.3 |
| 동료검토 계획서 | VWAY.PR (사내 프로세스, 5절 참고) |
| 형상관리 계획서 | SUP.8 |
| 문제해결관리 계획서 | SUP.9 |
| 품질보증 계획서 | SUP.1 |
| 변경요청 관리 계획서 | SUP.10 |
| 위험관리 계획서 | MAN.5 |
| 시스템 요구사항 명세서 | SYS.2 |
| 시스템 아키텍처 설계서 | SYS.3 |
| 시스템 통합 및 통합 검증 계획서 / 시스템 통합 테스트 케이스 | SYS.4 |
| 시스템 요구사항 검증 계획서 / 시스템 요구사항 테스트 케이스 | SYS.5 |
| 소프트웨어 요구사항 명세서 | SWE.1 |
| 소프트웨어 아키텍처 설계서 | SWE.2 |
| 소프트웨어 상세 설계서 / 소프트웨어 소스코드 | SWE.3 |
| 소프트웨어 유닛 검증 계획서 / 소프트웨어 유닛 테스트 케이스 | SWE.4 |
| 소프트웨어 컴포넌트(컴포너트) 검증 및 통합 검증 계획서 / 테스트 및 통합 테스트 케이스 | SWE.5 |
| 소프트웨어 요구사항 검증 계획서 / 소프트웨어 요구사항 테스트 케이스 | SWE.6 |

표에 없는 시트 이름은 프로세스를 비운 채 가져오고 "프로세스 지정 필요" 경고를 낸다.

### 3.2 프로세스 체크리스트 — `품질심사 프로세스 체크리스트_25년.xlsx`

- `표지`, `개정이력` 시트는 무시하고 **`양식` 시트**만 읽는다.
- 2~3행이 병합 헤더: `항목 ID | 프로세스 | 심사 항목 | 평가(판단, 점수) | 참고 | 비고`. 4행부터 데이터.
- 열 위치: A 항목 ID, B 프로세스(한글 이름), C 심사 항목, D 판단(충족/부분충족/미충족/NA), E 점수(1/0.5/0), F 참고, G 비고(단계: 분석·설계 및 구현·검증·계획·모든단계 등).
- 헤더 행은 B열이 `프로세스`인 행을 찾아 정하고, 그 다음다음 행부터 읽는다(병합 헤더 두 줄).
- 프로세스 이름과 심사 항목이 모두 빈 행, 그리고 합계 행(F열이 `프로세스 준수율`)은 건너뛴다.
- 항목 ID는 첫 행에만 `QA-XXX-001`이 있고 나머지는 비어 있다. **ID가 없는 행은 `QA-<프로세스ID>-<순번 3자리>`로 자동 부여**한다(예: `QA-SYS.2-001`). 엑셀에 ID가 있어도 `XXX` 같은 자리표시자면 자동 부여 규칙을 따른다. 판단·점수 열은 템플릿 예시값이므로 **가져오지 않는다**.

프로세스 한글 이름 → ASPICE ID 기본 대응(이름의 공백 차이는 무시):

| 엑셀 프로세스 이름 | ID |
|---|---|
| 시스템 요구사항 분석 | SYS.2 |
| 시스템 아키텍처 설계 | SYS.3 |
| 시스템 통합 및 통합 검증 | SYS.4 |
| 시스템 요구사항 검증 | SYS.5 |
| 소프트웨어 요구사항 분석 | SWE.1 |
| 소프트웨어 아키텍처 설계 | SWE.2 |
| 소프트웨어 상세 설계 및 구현 | SWE.3 |
| 소프트웨어 단위 검증 | SWE.4 |
| 소프트웨어 컴포넌트 검증 및 통합 검증 | SWE.5 |
| 소프트웨어 요구사항 검증 | SWE.6 |
| 프로젝트 관리 | MAN.3 |
| 형상관리 | SUP.8 |
| 문제해결 관리 | SUP.9 |
| 변경 요청 관리 | SUP.10 |
| 산출물 동료 검토 | VWAY.PR |

대응표에 없는 이름은 오류 목록에 올리고, QA가 프로세스를 지정해야 그 항목을 확정할 수 있다.

### 3.3 추가 지원 형식 (2026-10-27 사용자 승인)

3.1·3.2 형식에 더해 아래 VWAY 체크리스트 변형도 그대로 가져온다. 열 매핑 화면은 여전히 없다(비목표). 3.1·3.2 형식의 가져오기 결과는 바뀌지 않는다(단, 아래 6·7번의 빈 체크 ID·머리글 없는 시트 처리는 이 절을 따른다).

| 형식 | 예 | 특징 |
|---|---|---|
| A | 통합임포트(3.1) | 1행 codebeamer 필드명 |
| B | 4.0 통합형, 4.1 통합형, 동료검토 v2 | 시트별 산출물, 제목 행 아래 2~4행에 한글 머리글 `No. \| 체크리스트 ID \| 영역 \| 검토항목 \| 적용여부 …[\| 근거 (ASPICE 4.1 BP/OII·Guideline) \| 변경구분]`. 4.1은 머리글 위에 `관련 프로세스: MAN.3 …` 줄과 `산출물 목록` 시트(시트·ID 접두어·관련 프로세스)가 있다. 동료검토 v2는 체크리스트 ID 열이 비어 있다. |
| C | 품질심사 프로세스(3.2) | `양식` 시트 |
| C' | 4.1 통합형 프로세스 감사 | `통합 프로세스 감사` 시트, `항목 ID \| 프로세스 \| 심사 항목 \| 평가 \| \| 참고 (BP, PAM 4.1) \| 비고 (단계) \| …`, 프로세스 칸이 `공급자 모니터링 (ACQ.4)`, 실제 ID(`QA-ACQ4-001`), 프로세스별 그룹 제목 행 |
| D | 산출물 심사(한 시트) | `양식` 시트, `항목 ID \| 프로세스 \| 산출물 \| 심사 항목 \| 평가 \| \| 참고 \| 비고` |

1. **머리글 찾기(공통, `src/qa/headerDetect.js`)**: 시트마다 처음 비어 있지 않은 10행에서 머리글 행을 찾는다. 셀 글자는 공백을 모두 지우고 소문자로 바꿔 비교한다.
   - 체크 ID: `item_id`, `체크리스트id`, `체크리트스id`, `항목id` · 질문: `item_title`, `검토항목`, `검토항목(필수)`, `심사항목`
   - 영역: `col06`, `영역` · 적용 여부: `col35`, `적용여부` · 산출물: `산출물` · 프로세스: `프로세스` · 근거(basis): `근거`·`참고`로 시작 · 단계: `비고`로 시작
   - 머리글 행 = 질문 + (체크 ID 또는 프로세스 또는 산출물). 데이터는 다음 행부터이며, 바로 뒤의 `판단`/`점수` 보조 머리글 행과 두 번째 머리글 행(codebeamer 필드명 다음의 한글 머리글)은 건너뛴다.
   - 산출물 체크리스트는 `프로세스` 열이 있고 `산출물` 열이 없는 시트를 받지 않고(프로세스 체크리스트), 프로세스 체크리스트는 `프로세스`·질문 열이 있고 `산출물` 열이 없는 시트만 받는다.
2. **건너뛰는 시트**: 이름에 `표지`, `개정이력`, `작성 기준`, `작성기준`, `산출물 목록`, `요약`, `변경사항`, `판정규칙`, `전체 통합`, `목차`가 들어가거나 `CL2`로 시작하는 시트(GP 매트릭스)는 오류·경고 없이 건너뛴다. `전체 통합`은 머리글이 있어도 모든 항목의 중복이므로 건너뛴다. 그 밖에 머리글이 없는 시트는 경고 "머리글을 찾지 못해 건너뜀" 하나를 낸다.
3. **형식 오류**: 머리글이 있는 시트가 하나도 없을 때만 파일 단위 오류 하나를 낸다. 메시지에 시트마다 처음 비어 있지 않은 행의 앞 셀(최대 5개)을 붙여 무엇이 들어 있었는지 보여준다.
4. **산출물 항목의 프로세스** 결정 순서: QA의 시트 지정 → 행의 `프로세스` 칸에 있는 ASPICE ID(`ACQ.4` 등) 또는 3.2 이름 대응 → 머리글 위 `관련 프로세스:` 줄의 첫 ASPICE ID → `산출물 목록` 시트에서 시트 이름이 같은 행의 관련 프로세스 → 3.1 시트 이름 대응. 정하지 못하면 비워 두고 "프로세스 지정 필요" 경고를 낸다(시트당 한 번, `프로세스` 열이 있는 D 형식은 대응하지 못한 프로세스 값마다 한 번).
5. **산출물 이름**: `산출물` 열 값이 있으면 그 값, 없으면 시트 이름에서 번호를 뺀 이름(3.1).
6. **빈 체크 ID 자동 부여**: 질문은 있는데 체크 ID가 비면 오류 대신 ID를 만든다. 접두어는 `산출물 목록`의 ID 접두어 → `CH-<시트 앞 번호>` → `CH-WP` 순이며, 접두어별로 `-001`부터 세고 파일 안의 실제 ID와 겹치는 번호는 건너뛴다. 질문이 빈 행(ID만 있음)은 지금처럼 오류다.
7. **그룹 제목 행**(질문 없이 공백이 든 글 한 칸만 있는 행, 예: `ACQ.4 공급자 모니터링 … — VDA 범위: Flex`)과 합계 행(`프로세스 준수율`)은 말없이 건너뛴다.
8. **근거(basis)**: 근거·참고 열의 글을 항목의 `basis`(없으면 `""`)로 저장한다(산출물·프로세스 항목 모두). AI 초안 요청에 함께 보내 관련 BP를 고르는 힌트로만 쓰며, 응답 정제 규칙(배치 프로세스의 BP만 남김)은 그대로다.
9. **프로세스 체크리스트**: 같은 머리글 찾기를 모든 시트에 적용하고, 체크 ID 열까지 있는 시트가 있으면 그 시트만 읽는다. 프로세스 칸은 QA 이름 지정 → 괄호 안 ASPICE ID → 3.2 이름 대응 순으로 정한다. 자리표시자가 아닌 엑셀 ID는 그대로 쓴다.

## 4. 가져오기 검증 (오류 목록)

가져오기 직후 아래를 검사해 **오류(확정 불가)**와 **경고(확정 가능)**로 나눠 보여준다. 각 줄에는 파일·시트·행 번호를 표시한다.

| 검사 | 등급 |
|---|---|
| 머리글 행이 있는 시트가 하나도 없음(3.3) | 오류(파일 전체 미가져오기) |
| 머리글 행이 없는 시트(건너뛰는 시트 제외, 3.3) | 경고(해당 시트 미가져오기) |
| 검토 항목 빈칸(체크 ID만 있음), 프로세스 체크리스트의 프로세스 이름 빈칸 | 오류(해당 행) — 빈 체크 ID는 자동 부여(3.3) |
| 같은 파일 안 체크 ID 중복 | 오류(두 번째 이후 행) |
| 시트 이름·프로세스 이름이 대응표에 없음 | 경고 — QA가 지정 |
| 관련 BP가 ASPICE 4.0 BP 목록(`packages/harness/spec/canonical/processes/*.json`)에 없음 | 오류(확정 시 검사) |
| 프로세스 체크 항목의 연결 산출물 체크 ID가 존재하지 않음 | 오류(확정 시 검사) |
| 프로세스 체크 항목에 연결이 하나도 없음 | 경고 "연결 필요" — 확정은 막는다(6.2) |

오류가 있어도 나머지 행은 가져온다. 사용자는 오류 행을 엑셀에서 고쳐 다시 가져오거나, 화면에서 해당 항목을 보완한다.

## 5. 사내 프로세스 VWAY.PR

"산출물 동료 검토"와 "동료검토 계획서"는 ASPICE 4.0 32개 프로세스에 대응하는 것이 없다. 1단계에서는 고정 ID `VWAY.PR`(이름: 산출물 동료 검토)로 저장하고 **관련 BP는 비워 두는 것을 허용**한다. 관련 BP가 없는 항목은 이후 프로세스 준수율에는 포함되지만 BP 등급 계산에서는 빠진다. — 내 판단(빌더가 다른 방식이 낫다고 보면 바꿀 수 있음).

## 6. 데이터 모델

모두 IndexedDB(`src/utils/idb.js`)에 저장한다. 키는 기존 키와 겹치지 않게 `aspice_qa_` 접두어를 쓴다.

체크리스트 세트는 **브라우저(PC)당 하나를 모든 로그인 사용자가 같이 쓴다**. 사용자별로 나누지 않고, 확정한 사람은 `confirmedBy`로만 기록한다. 1단계는 PC 한 대에 담당 QA 한 명을 가정한다(사용자 결정).

```
ChecklistSet (키: aspice_qa_checklists → { activeVersionId, versions: [ChecklistVersion] })

ChecklistVersion {
  id, version (1부터 증가), createdAt, createdBy,
  sources: [{ kind: "wp"|"process", fileName, sheetNames, importedAt }],
  wpItems: [WpCheckItem],
  processItems: [ProcessCheckItem],
  importIssues: [{ level: "error"|"warning", file, sheet, row, message }]
}

WpCheckItem {
  checkId,               // CH-PP-001 (엑셀 원문, 읽기 전용)
  workProduct,           // 시트 이름에서 번호 제거: "프로젝트계획서"
  sheet, row,            // 원본 위치
  processId,             // MAN.3 (시트 대응표, QA 수정 가능)
  area, question,        // 엑셀 원문, 읽기 전용
  applicable,            // bool
  basis,                 // 근거 열 원문 (없으면 "", 3.3)
  raw,                   // 원본 행 전체
  draft:  WpCriteria | null,   // AI 초안 (보관용, 판정에 안 씀)
  confirmed: WpCriteria | null,// QA 확정본 (판정에 씀)
  status: "pending" | "drafted" | "confirmed" | "stale",
  confirmedBy, confirmedAt,
  customRuleIds: []      // 2단계에서 사용, 1단계는 항상 []
}

WpCriteria {
  criteria: [{ id: "CH-PP-003-1", text }],  // 판정 기준(세부 규칙), 한 개 이상
  polarity: "positive" | "negative",        // negative = 질문에 '예'면 Fail ("오타가 존재하는가?")
  targetLocations: [string],                // "4. Organization Chart", "4.1 Role and Responsibility 표"
  relatedBPs: ["MAN.3.BP5"],               // 0개 이상
  severity: "상" | "중" | "하"
}

ProcessCheckItem {
  itemId,                // QA-SYS.2-001 (자동 부여 또는 엑셀)
  processName,           // 엑셀 원문
  processId,             // SYS.2 (대응표, QA 수정 가능)
  question, phase,       // 심사 항목, 비고(단계) — 원문, 읽기 전용
  basis,                 // 참고 열 원문 (없으면 "", 3.3)
  row,
  draft: ProcCriteria | null,
  confirmed: ProcCriteria | null,
  status: "pending" | "drafted" | "confirmed" | "stale",
  confirmedBy, confirmedAt
}

ProcCriteria {
  linkedWpCheckIds: ["CH-SR-004", ...],  // 1개 이상 (확정 조건)
  relatedBPs: ["SYS.2.BP2"],             // VWAY.PR은 0개 허용
  aggregation: "default"                 // 6.3 규칙. 1단계는 default만
}
```

### 6.1 상태 규칙

- `pending`: 가져오기만 됨. `drafted`: AI 초안 있음. `confirmed`: QA 확정. `stale`: 확정 후 원문이 바뀜(6.4).
- **판정(3단계)은 `status === "confirmed"`인 항목의 `confirmed`만 읽는다.** `draft`는 어떤 경우에도 판정에 쓰지 않는다.
- QA가 확정 후 다시 수정하면 `confirmed`를 덮어쓰고 `confirmedAt`을 갱신한다.

### 6.2 확정 조건

- 산출물 항목: 판정 기준 1개 이상, 관련 BP가 모두 유효(VWAY.PR 예외), 심각도 지정, `processId` 지정. 대상 위치는 비워도 확정 가능(경고만).
- 프로세스 항목: 연결 산출물 체크 ID 1개 이상이고 모두 같은 버전 안에 존재, 관련 BP 유효(VWAY.PR 예외), `processId` 지정.
- 연결된 산출물 항목이 아직 확정되지 않았어도 프로세스 항목은 확정할 수 있다(3단계에서 미확정 연결 항목은 "보류"로 처리).

### 6.3 프로세스 항목 집계 규칙 (3단계 구현용, 1단계에서 정의만)

연결된 **확정** 산출물 항목들의 결과로 판정한다.
- 모두 Pass → 충족(1) / 일부 Pass → 부분충족(0.5) / 모두 Fail → 미충족(0)
- 모두 NA(적용 안 함) → NA
- 하나라도 보류 → 보류(QA 확인 전까지 준수율 계산 제외)
- 프로세스 준수율 = 점수 합 ÷ (NA·보류 제외 항목 수). 준수율 옆에 제안 문서 3.2의 NPLF 등급(N 0~15, P- ~32.5, P+ ~50, L- ~67.5, L+ ~85, F ~100, 하한 초과·상한 이하)을 표시한다.

### 6.4 다시 가져오기와 버전

- 다시 가져오기는 항상 **새 버전**을 만든다. 이전 버전은 그대로 남고, 보고서는 사용한 버전 번호를 기록한다(3단계).
- 새 버전에서 체크 ID가 같은 항목:
  - 검토 항목 원문이 같으면 이전 버전의 `draft`·`confirmed`·`status`를 그대로 이어받는다.
  - 원문이 바뀌었으면 `confirmed`는 참고용으로 복사하되 `status = "stale"`로 두고 QA 재확정을 요구한다.
- 이전 버전에만 있던 항목은 새 버전에 없다. 가져오기 결과 요약에 "삭제됨 N건"으로 보여준다.
- 프로세스 항목은 자동 부여 ID라 순서가 바뀌면 ID가 달라질 수 있다. 그래서 이어받기는 **(processId, 심사 항목 원문)** 쌍으로 맞춘다.
- 활성 버전(`activeVersionId`)은 하나다. 새로 가져오면 그 버전이 활성 버전이 된다. 이전 버전으로 되돌리기는 버전 목록에서 "활성으로 지정"으로 한다.

병합은 아래 순서로 한다(내 판단).

1. **QA 수동 지정 복원**: QA가 바꾼 시트→프로세스 지정, 대응표에 없던 프로세스 이름→ID 지정을 `ChecklistSet.mappingOverrides`(`{ sheets: {<원본 시트 이름 전체>: processId}, processNames: {<엑셀 프로세스 이름>: processId} }`)에 저장해 두고, 새 버전 파싱 직후 기본 대응표보다 먼저 적용한다. 시트 키는 번호까지 포함한 원본 이름 전체를 쓴다(두 `22.` 시트를 구분하기 위해).
2. **산출물 항목 이어받기**: 체크 ID로 맞춘다(위 규칙).
3. **프로세스 항목 이어받기**: (processId, 심사 항목 원문)으로 먼저 맞춘다. 맞지 않으면 엑셀에 실제 ID(자리표시자 아님)가 있을 때 그 ID로, 그것도 없으면 같은 processId 안의 순번으로 맞추고, 이렇게 맞춘 항목은 `stale`로 둔다. 어느 방식으로도 맞지 않을 때만 삭제+신규로 처리한다.
4. **연결 재검사**: 확정된 프로세스 항목의 `linkedWpCheckIds` 중 새 버전에 없는 ID가 있거나 연결된 산출물 항목이 `stale`이 되면, 그 프로세스 항목도 `stale`로 바꾼다. 없어진 ID는 **지우지 않고** 편집 화면에 "없는 항목"으로 표시해 QA가 직접 빼게 한다.

한 파일만 다시 가져오면, 다른 쪽 항목은 활성 버전에서 상태·확정 내용을 그대로 복사한 뒤 위 4번 연결 재검사만 다시 실행한다.

## 7. AI 초안 생성

### 7.1 방식

- 새 서버 엔드포인트 `POST /api/qa-draft`를 추가한다. `api/project.js`와 같은 인증·CORS 처리를 쓰고, 개발 서버에서는 `vite.config.js`의 기존 미들웨어 패턴으로 연결한다.
- 서버는 `packages/harness`의 `createLlmClient`(기존 공급자 설정, 기본 Anthropic)를 사용한다.
- 요청 단위: 산출물 시트 하나(또는 프로세스 하나)의 항목 묶음. 항목 수가 많으면 20개 단위로 나눈다. 동시 요청 수는 기존 채점 기본값과 같은 5.
- 사용자는 "AI 초안 만들기"를 버전 전체, 시트(프로세스) 단위, 항목 단위로 실행할 수 있다. 이미 `confirmed`인 항목은 기본적으로 건너뛴다.

### 7.2 산출물 항목 초안 입력·출력

입력: 산출물 이름, 프로세스 ID, 해당 프로세스의 BP 목록(ID·이름·설명, `spec/canonical/processes/<ID>.json`), 항목들의 `checkId`·`area`·`question`.

출력(항목별 JSON): `criteria[]`(검증 가능한 문장, 1~5개), `polarity`, `targetLocations[]`(산출물의 예상 절·표 이름), `relatedBPs[]`(입력으로 준 BP 목록 안에서만), `severity`, `rationale`(한 문장, 화면에 참고로만 표시).

서버는 응답을 검증한다: 목록에 없는 BP ID는 제거, 심각도 값이 상/중/하가 아니면 "중", criteria가 비면 그 항목은 실패로 표시. 실패한 항목은 `pending`으로 남기고 화면에 이유를 보여준다.

### 7.3 프로세스 항목 초안 입력·출력

입력: 프로세스 ID와 BP 목록, 해당 프로세스 항목들의 `question`, 그리고 **같은 버전의 산출물 항목 후보**(같은 processId인 산출물 항목의 `checkId`·`workProduct`·`question`). MAN.3처럼 여러 산출물(프로젝트계획서·위험관리 계획서 등)이 관련될 수 있으므로, 후보는 같은 processId 항목 전체 + 다른 processId 항목 중 이 프로세스의 관련 BP를 가진 확정 항목으로 한다.

출력(항목별): `linkedWpCheckIds[]`(후보 안에서만), `relatedBPs[]`, `rationale`. 서버는 후보 밖 ID를 제거한다.

2. **가져오기 결과 요약**: 버전 번호, 산출물 항목 수 / 프로세스 항목 수, 이어받음·변경됨(stale)·신규·삭제 건수, 오류·경고 목록(파일·시트·행).
3. **진행 현황**: 산출물·프로세스별 `pending / drafted / confirmed / stale` 건수와 확정률. "AI 초안 만들기" 버튼.
4. **항목 목록**: 왼쪽에 산출물(시트)·프로세스 트리, 오른쪽에 항목 표(ID, 영역/단계, 검토 항목, 상태, 심각도). 상태로 필터.
5. **항목 확정 패널**(항목 클릭 시):
   - 위: 엑셀 원문(체크 ID, 영역, 검토 항목, 원본 시트·행) — 읽기 전용.
   - 아래: AI 초안을 미리 채운 편집 폼.
     - 산출물 항목: **판정 기준**(추가·삭제·수정, 기준 ID 자동), 극성(긍정/부정 질문), **대상 위치**(여러 개, 자유 입력), **관련 BP**(해당 프로세스 BP 목록에서 다중 선택, 다른 프로세스 BP도 검색해 추가 가능), **심각도**(상/중/하), 프로세스 지정.
     - 프로세스 항목: **연결 산출물 체크 ID**(검색·다중 선택, 각 항목의 검토 항목 문장 미리보기), **관련 BP**, 프로세스 지정.
     - AI `rationale`은 폼 옆에 회색 참고 문구로만 보여준다.
   - 버튼: "확정", "초안 다시 만들기", "확정 취소"(→ drafted). 확정 조건(6.2)을 못 채우면 "확정"을 비활성화하고 이유를 표시한다.
   - 여러 항목을 골라 "초안 그대로 일괄 확정"할 수 있다. 확정 조건을 못 채운 항목은 제외하고 건수를 알린다.
6. **버전 목록**: 버전·가져온 시각·원본 파일명·확정률. "활성으로 지정", "JSON 내보내기". JSON 가져오기는 1단계 범위 밖.

`confirmedBy`에는 기존 로그인 사용자(`src/auth/userStore.js`의 현재 사용자) 이름을 넣는다.

## 9. 코드 배치 (기존 관례를 따름)

- 엑셀 파싱·검증·버전 병합은 **순수 함수**로 `packages/harness/src/qa/`에 둔다(예: `importWpChecklist.js`, `importProcessChecklist.js`, `validateChecklist.js`, `mergeVersion.js`, `processNameMap.js`). 브라우저에서는 `xlsx`로 읽은 시트 배열을 이 함수들에 넘긴다. 서버(초안 생성)도 같은 모듈의 BP 목록·검증 함수를 쓴다.
- 프롬프트는 `packages/harness/src/llm/prompts/`에 `qaWpDraftPrompt.js`, `qaProcessDraftPrompt.js`로 추가한다.
- 서버 처리: `api/qa-draft.js`(Vercel 함수) + 처리 로직은 `api/_harnessService.js` 옆 새 파일 또는 그 안에 `handleQaDraft`.
- 프런트: `src/components/qa/`(QaAuditView, ChecklistImportPanel, ChecklistItemTable, ChecklistItemEditor, ChecklistVersionList), 상태는 `src/hooks/useQaChecklist.js`(IndexedDB 읽기·쓰기, 기존 `useCustomRules.js` 패턴).
- 스타일은 기존과 같이 `src/theme.js` 인라인 스타일, 아이콘은 lucide-react.

## 12. 내 판단으로 정한 것 (사용자 확인 전)

- 다시 가져오면 새 버전 생성, 같은 체크 ID(프로세스는 프로세스+문장) 확정 내용 이어받기, 문장이 바뀌면 stale.
- 저장은 브라우저 IndexedDB (PC당 한 세트 공유는 사용자 결정).
- 프로세스 체크리스트 엑셀의 판단·점수 열은 예시값으로 보고 가져오지 않음.
- 프로세스 항목 ID 자동 부여 규칙 `QA-<프로세스ID>-<순번>`.
- 동료 검토를 사내 프로세스 `VWAY.PR`로 처리하고 관련 BP 없이 확정 허용.
- 집계 규칙(6.3)과 준수율 옆 NPLF 등급 표시.
- 부정형 질문("오타가 존재하는가?")을 위한 극성 필드.
- 병합 순서(6.4): QA 수동 지정 복원 → 항목 이어받기 → 프로세스 항목 대체 매칭(엑셀 ID → 순번, 이렇게 맞춘 항목은 stale) → 연결 재검사(없어진 연결·stale 연결이 있으면 프로세스 항목도 stale, 연결은 지우지 않음).
- 한 파일만 다시 가져오면 다른 쪽은 그대로 복사한 뒤 연결 재검사만 실행.
- 시트 이름 → 프로세스 대응표(3.1).
